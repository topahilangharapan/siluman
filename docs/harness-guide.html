no-tells: the human-writing harness, explained

Every writing request you make goes through this machinery. It injects your writing rules next to the prompt, then checks the finished reply three different ways, and rejects it until it reads like a person wrote it. Nothing here depends on the model choosing to comply: the checks are scripts and statistics.

Non-writing turns skip all of this. The gate disarms the flag file, no rules are injected, and the linter exits before doing any work. Your coding sessions pay zero cost.

Tier 1: hard bans

Only things that are wrong in any quantity live here, and they are all mechanical formatting, so a regex is the right tool. Vocabulary was removed from this tier on purpose: words are handled statistically in tier 2, because banning "crucial" outright is not how humans write either.

Tier 2: statistics instead of bans

Your objection to v1 was right: humans do say "crucial", just not the way AI does. So each tell word now carries a baseline, called lambda: the rate a careful human writer plausibly uses it per 1000 words. "Delve" gets 0.02 because people nearly never write it. "Crucial" gets 0.8 because people do.

When your reply comes in, the linter counts each term and asks one question: how surprising is this count if a human wrote the text? That is a Poisson tail probability. Each surprise converts to a z-score on the normal distribution, the z-scores combine across all terms (Stouffer's method: sum divided by the square root of how many), and the reply blocks only when the combined score passes 3.0, roughly a one-in-a-thousand chance for human writing.

Worked example. One "crucial" in a 400-word email: expected count 0.32, seeing 1 has probability 0.27, z = 0.6. Passes without comment. Two "delve" in 176 words: expected count 0.0035, seeing 2 has probability near 0.000006, z = 4.4. Blocked. Same machinery, no word list ban, just how far the text sits from human behavior.

Two more checks run in this tier, both pure statistics:

  • Clustering. Three or more distinct tell words inside any 100-word window blocks even when the whole-document rate looks fine. AI tells arrive in bunches; human use of the same words is scattered.
  • Burstiness. For text over 150 words, the linter measures how much sentence lengths vary (standard deviation over mean). Human rhythm is irregular. When the variation drops below 0.35, the text reads metronome-uniform and gets sent back with the instruction to vary sentence lengths.

Every lambda and threshold lives in lint-rules.json, so tuning is a data edit, not a code change.

Tier 3: the semantic judge

Regex cannot tell "navigate the city" from "navigate the landscape of ideas". A language model can. So after the mechanical tiers, the hook shells out to a small, fast, cheap Claude model (Haiku) running headlessly:

claude -p --model claude-haiku-4-5-20251001 \
  --settings '{"disableAllHooks":true}'  # no recursion into our own hooks \
  --no-session-persistence --output-format json \
  "<judge prompt with criteria + your reply's text>"

The judge answers in strict JSON with a pass verdict and quoted violations. It checks the things only context can reveal: figurative cliches, significance inflation, legacy padding, weasel attribution ("experts believe" with no expert named), promotional tone, analysis bolted onto facts, synonym rotation, restated requests, canned politeness, triplet overuse.

From today's verification run, against a mechanically clean but AI-flavored paragraph, it returned all five planted violations with exact quotes, including catching "metropolis / urban hub / city" as synonym rotation for the same referent. The full round trip took about 12 seconds and two cents.

Fail-open by design. If the judge times out, errors, or returns something unparseable, tiers 1 and 2 stand alone and you get a visible note that the judge was skipped. A network problem can never trap your session behind an unreachable check.

The rewrite loop

  1. All three tiers run and their findings merge into one list, so a single rewrite fixes everything at once instead of ping-ponging through separate blocks.
  2. On violations, the hook returns a block decision. The reply you would have seen is discarded, and Claude receives the list with exact quotes: which em dash, which word at what multiple of the human rate, which sentence the judge flagged and why.
  3. Claude rewrites. The new text goes through all three tiers again, fresh.
  4. A counter in the session flag file caps this at 2 rewrites. If violations somehow survive both, the turn releases anyway and prints a warning listing what remains, so enforcement fails loudly rather than looping forever or failing silently.

Operating notes

  • Force enforcement on any prompt by including #hw.
  • Say "refresh the writing preset" every 2 or 3 months: the skill re-reads Wikipedia's signs-of-AI-writing page, updates the preset and the lambda list, and never touches your em-dash rule or overrides file.
  • Tune sensitivity in lint-rules.json: raise a word's lambda if it keeps flagging your natural vocabulary, raise composite_z_threshold to loosen the whole tier, set semantic_judge.enabled to false to skip the judge and its 2-cent, 12-second cost.
  • Writing turns take roughly 12 extra seconds when the judge is on. Coding turns are untouched.
